Omissis

A local layer that pseudonymises Italian text before it reaches a cloud LLM, puts the real values back in the reply, and measures what that costs in privacy and in answer quality.

Giuseppe · Andrea · Mattia

[0:20 · Giuseppe] Omissis is Latin for "things left out". It sits between you and a cloud model: it hides who you are before the text leaves your machine, and puts the real values back in the answer. The tool is half of the project; the other half, the contribution, is the measurement of what that hiding costs.

[1:30 · Giuseppe] The loop of masking, sending and restoring already exists. Presidio detects and anonymises personal data and documents a de-anonymise operator; it is our detector D1. Ready-made PII classifiers from model hubs are our detector D2. LLM Guard, now archived, pairs an anonymise scanner and a vault with a de-anonymise scanner, and LangChain's experimental reversible anonymizer keeps a mapping and applies it back. So we did not invent the loop, and we reuse two of these tools inside it. What none of them tells you is how much the masked text still reveals, and what masking costs the reply. That is what we add.

[1:30 · Giuseppe] Three lines of research. First, Staab and colleagues showed that LLMs infer personal attributes, location, income, sex, from ordinary text; our attribute attack asks the same question with closed lists. Second, the same group used an adversary model to guide what to rewrite; we use the adversary only to measure. Third, the text-anonymisation benchmark TAB and the work of Lison and colleagues argue that anonymisation must be scored for disclosure risk and utility together, not only by labelling accuracy; we follow that, on Italian synthetic data, much smaller. On the legal side: the GDPR defines pseudonymisation, the EDPB has draft guidelines, and the Court of Justice held in 2025 that pseudonymised data are not personal data in every case and for every recipient. Part 3

Six stages: only the masked text crosses to the cloud

this machine
cloud
this machine

Detect

Five detectors, from rules to a local LLM; one overlap rule merges them.

Resolve

Mentions of one person become one entity, with grammatical gender.

Replace

R1 typed placeholders or R2 realistic fakes, kept in an in-memory vault.

Send

One function for every LLM call; cached, temperature 0.

Restore

Exact, normalised, then fuzzy matching. Never a guess.

Report

The reply with real values, plus what was replaced and what could not be put back.

R1  mi chiamo [PERSONA_1_M], conto [IBAN_1]

R2  mi chiamo Leandro Zambelli, conto IT13O0000… (a bank code no bank has)

[1:00 · Mattia] One row, six stages. Detect finds sensitive spans with one of five detectors. Resolve groups the mentions of the same person into one entity and infers grammatical gender from rules. Replace swaps each entity for a placeholder, R1, or a realistic fake, R2, and records the mapping in a vault that lives in memory only. Send is the only step that talks to the cloud, and every model call in the project goes through one cached function. Restore puts the real values back: exact match, then normalised, then fuzzy; what it cannot place it reports, it never guesses. Everything except the cloud call runs on the user's machine, including the local LLM used by D3.

Part 3

Five design choices, each with its reason

01

Three classes of span

Masking is decided per class; two references isolate what hiding quasi-identifiers buys.

02

Text, not offsets

The local LLM returns span text, found by string search: a span it invents is dropped.

03

[PERSONA_1_F]

Gender keeps Italian agreement right. Its cost is measured: the attacker reads gender.

04

Never guess

A token restoration cannot resolve is reported to the user, never filled in.

05

Refuse the impossible

A sum of masked amounts is stopped before sending: no number, or a wrong one.

The text is pseudonymised, not anonymised: what we measure is its re-identification risk.

[1:00 · Mattia] Five choices that shaped the system. The three classes let us separate what masking quasi-identifiers buys. The local LLM never gives offsets, because models are bad at counting characters; it gives text, we find it, and an invented span simply cannot be placed. Placeholders carry gender so that Italian agreement stays right, and we pay for it: the attacker reads gender from them. Restoration never guesses. And a request that masking makes impossible, like adding up masked amounts, is refused rather than answered wrong; that check is a heuristic and we did not evaluate it.

Part 3

Five detectors, from cheap and predictable to slow and general

D0 · Rules

IBAN, codice fiscale, P. IVA, phone, email, amounts next to a currency; most with a checksum.

Misses everything without a shape: names, towns, employers, health.

D1 · Presidio + spaCy it_core_news_lg

Names, places, organisations; Italian pattern recognisers.

No date label beyond numeric dates; no job, age or health.

D2 · PII classifier piiranha, as shipped

Names, emails, phones, tax and account numbers.

Only one quasi label (town); often covers part of an email. Non-commercial licence.

D3 · Local LLM gpt-oss:20b on this machine

Job, employer, town, age, health, union, user codes; JSON with a reason.

Slowest; two invalid replies mean no spans for that text.

D4 · Hybrid

Direct identifiers from D0, D1, D2; everything else from D3. No new logic.

Inherits D1's type errors: a company masked as a person.

[1:00 · Mattia] The five detectors. D0 is regular expressions with checksums: exact, and blind to anything without a shape. D1 is Presidio with the Italian spaCy model, the standard off-the-shelf choice and the baseline of our first contrast. D2 is a ready-made multilingual PII classifier used as it ships; its licence is non-commercial. D3 is a local LLM, gpt-oss 20B through Ollama on the laptop, so the unmasked text never leaves the machine; it returns span text, type and a reason. D4 is composition only: direct identifiers from the first three, the rest from D3. D1 was added to D4 after the pilot, where D2 alone missed person names.

  1. The attacker LLM reads the masked text and ranks the candidates.
  2. Linkage top-1: share of texts where its first pick is the author.
  3. A second attack guesses city, role, employer, age, gender and health.

Privacy score = 1 − linkage top-1

Three contrasts declared before any result, Holm-corrected at α = 0.05.

[1:00 · Andrea] The privacy measure is a re-identification attack. An attacker model sees the masked text and 25 candidate profiles, one of them the author, and must rank them. Linkage top-1 is how often its first choice is right; by chance that is 4 percent. Privacy score is one minus that. A second attack guesses six attributes from closed lists. The three comparisons we test were declared before any result, with a Holm correction for multiple testing.

Leave the quasi-identifiers visible and the author is named almost every time: D1+R1 0.93, D2+R1 1.00.

Mask everything the annotation marks and the attacker still names half the authors: REF-oracle 0.50.

What is left (topic, product, tone, cohort) still points to a person. Pseudonymisation lowers the risk; it does not remove it.

[1:10 · Andrea] Linkage top-1 with 25 candidates, lower is better, dashed line is chance at 0.04. With nothing masked the attacker is right every time. Masking only what Presidio or the classifier find barely moves it: 0.93 and 1.00, because they leave job, town and employer in clear. The hybrid brings it to 0.59 with placeholders and 0.41 with fakes. Even the oracle, masking every annotated span, stays at 0.50, more than ten times chance. Without the five loan texts whose content contradicts the author's profile, the hybrid is at 0.63 and 0.44: a control, not a test.

Limits: what these numbers do not tell you

Synthetic data

Written by one model: more regular than real mail.

No human annotator

An AI agent reviewed the gold and rated the judge's items; one member approved its reports.

The judge was rejected κ 0.37

0.6 was needed: T1 exists for D4+R1 only, rated by one member.

One hosted model

The cloud model, the attacker and the judge; no external data, no linking across texts.

Optimistic intervals

Texts by the same author are not independent.

Pseudonymisation, not anonymisation

We measure re-identification risk, not legal anonymity.

How a user
gets it
Apps on an API: yesThe app calls Omissis first; users install nothing. The case we built.

[1:20 · Mattia] What these numbers do not say. Synthetic data, written by one model. No human annotated or rated since 21 November: an AI agent did, and one member approved its reports. The judge for drafted replies failed its validation, kappa 0.37 against 0.6, so the reply score exists only for the hybrid. One attacker, no outside data. Texts by the same author are not independent, so our intervals are optimistic. And this is pseudonymisation, never an anonymous text. Last, the question we were asked: how would someone actually use it? What matters is whether the user's software lets you choose where its requests go. An application that calls a model through an API, say a bank's assistant for its staff, does: the company adds Omissis before the call and restores the reply, and the end user installs nothing. That is the case we built and measured, one message and one reply. Coding agents like Claude Code or Codex also talk to an API, and both let you point them at a local proxy, so in principle the same layer fits. In practice every request resends the whole session, mostly code rather than Italian mail; running a local LLM over it on every turn is too slow, and the vault has to last the whole session, which we did not build. Consumer chat apps like ChatGPT or Claude.ai are the hard case: the text goes from the browser straight to the vendor, with no setting to redirect it. The only hook is a browser extension that rewrites the text box and the reply on the page: fragile, and attachments go around it. Our app cannot stand in by copy and paste either: it sends the text itself, and its vault is erased, so a reply pasted back could not be restored.
